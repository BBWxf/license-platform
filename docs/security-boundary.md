# 安全边界与威胁模型

## 1. 当前部署不能声称安全

当前默认入口是固定公网 IPv4 上的 HTTP 80。即使 Caddy、容器隔离、root-only secret 和数据库内部网络都配置正确，公网客户端到 Caddy 的链路仍然：

- 可被被动窃听；
- 可被主动篡改；
- 无法可靠认证服务端；
- 可能泄露后台口令、token、许可证和设备数据；
- 可能被劫持返回伪造公钥、许可结果或管理页面。

`--accept-insecure-http` 是风险确认，不是安全控制。防火墙、VPN 和来源白名单可以减少攻击面，但不能把裸 HTTP 转化为具有 TLS 属性的连接。生产目标应是域名 HTTPS。

## 2. 信任边界

### 受信任程度高

- Ubuntu/Debian 主机内核和 root 管理平面；
- Docker daemon；
- `/opt/license-platform` 的 root 管理文件；
- `/etc/license-platform` 的 root-only 配置与 secrets；
- `/var/backups/license-platform` 及其离线加密副本；
- 应用镜像和基础镜像供应链；
- 应用私钥解密密钥。

获取 Docker socket 基本等价于获取主机 root。能读取备份或应用解密密钥的主体能够恢复敏感数据/私钥，必须按最高敏感级别管理。

### 低信任或不受信任

- 公网客户端和公网链路；
- 客户端提供的所有标识、时间、设备信息和载荷；
- HTTP 头，包括未经可信代理约束的转发头；
- 容器日志、浏览器历史、支持包；
- 镜像标签指向的远端内容；
- 没有独立签名/来源证明的备份和升级包；
- 客户端本地存储与终端用户控制的运行环境。

## 3. 已实施的部署控制

- Compose 项目和服务名固定，运维脚本只操作本项目；
- 安装前检查端口冲突，不停止或修改其他容器；
- PostgreSQL 18 不发布主机端口；
- `backend` Docker 网络为 internal；
- `app` 不发布 8080；
- Caddy 是唯一入口；
- secrets 由安装器随机生成，宿主机父目录为 `root:root 0700`，文件为 `root:<SECRETS_GID> 0440`；普通宿主机用户无法遍历父目录；
- app 和 db 仅通过 numeric supplemental group 读取各自 bind-mounted file secret；
- PostgreSQL 使用 Docker secret 文件；应用入口把数据库口令写入 tmpfs 上的 `0600 /tmp/.pgpass`，连接串和进程环境不含口令；
- 应用解密密钥和引导口令通过文件路径挂载；
- 长期 app 进程显式固定为 UID/GID 1654 非 root、只读根文件系统、`cap_drop: ALL`、`no-new-privileges` 和资源限制，只保留 `/app/data` 与 `/tmp` 可写；安装/升级仅用一次性 root 容器和 `CHOWN/DAC_OVERRIDE/FOWNER` 校正数据卷所有权；
- Caddy 使用只读根文件系统、`no-new-privileges`、资源限制，并只增加绑定低端口所需的 `NET_BIND_SERVICE`；
- Caddy 去除 `Server` 响应头并设置基础浏览器安全头；
- Docker 日志有大小和文件数上限；
- 镜像禁止 `latest`，使用明确版本变量；
- 升级前备份，保存旧镜像回滚标签；
- 恢复和回滚要求精确确认词；
- 每日 systemd timer 已启用，保留 14 天本地备份；
- 脚本不提供自动删卷、全局 prune 或静默卸载。

这些控制降低部分风险，但不补偿公网 HTTP。

## 4. 明确未解决的风险

- 当前公网传输无 TLS；
- 明确版本标签仍可能被远端重指向，正式发布应固定 digest 并验证签名/SBOM；
- Docker daemon 和 root 主机失陷会突破全部容器边界；
- 单主机数据库和本地备份不能提供主机级灾难恢复或高可用；
- 本地备份未额外加密；
- 容器内部 app 到 db 的连接配置为 `SSL Mode=Disable`，依赖单主机 internal Docker 网络边界；
- 2 GiB 主机资源有限，构建、迁移、备份与流量并发可能造成可用性问题；
- 部署脚本无法替代应用层认证、授权、MFA、CSRF、输入验证、速率限制、审计和日志脱敏；
- 客户端处于终端用户控制环境，无法把嵌入客户端的共享秘密视为不可提取；
- SHA-256 校验可发现意外损坏，但如果归档和校验文件同时被攻击者替换，不能证明来源真实性。

## 5. secrets 边界

宿主机 secrets：

- `postgres_password`：数据库网络认证口令，应用容器入口从该文件在进程启动时组装连接串；
- `card_lookup_key`：卡号/查询值的 HMAC 查找材料；
- `master_encryption_key`：保护服务端签名私钥/敏感数据的主解密材料；
- `admin_initial_password`：首次后台引导材料。

要求：

- 不提交到 Git；
- 不输出到日志、命令行参数、聊天和工单；
- 不通过普通 SCP 临时目录长期留存；
- 宿主机必须通过 root-only 父目录阻止非 root 路径遍历；文件的专用 numeric group 只为容器内 supplemental group bind mount 提供读取；
- 不得把 `SECRETS_GID` 对应的宿主机组授予登录用户；
- 轮换前必须确认应用和数据库的原子切换方案；
- 解密密钥轮换必须考虑历史密文重加密和旧备份恢复；
- 从备份恢复口令后，要同步数据库角色口令；恢复脚本已执行该步骤；
- 初始后台口令首次使用后按应用规则轮换/禁用。

Docker secret 在非 Swarm Compose 中是文件挂载机制，不等同于外部 KMS/HSM。宿主机 root 和 Docker 管理员仍可访问。

### 卡密导出归档

每批原始卡密 CSV 使用现有 AES-GCM 服务和批次绑定的 purpose 加密保存，管理员可重复下载；下载不再清除存档，也不再按原 15 分钟门槛拒绝导出。单张卡密记录仍保存 HMAC 和提示，**加密 CSV 则是可恢复完整卡密的敏感归档，不是不可逆摘要**。

- 导出仅通过后台认证会话主动请求；每次仍验证管理员 credential stamp，不增加匿名或 bearer-token 下载链接。
- 完整卡密只出现在授权文件响应中，不进入普通页面、URL、审计摘要、日志或浏览器存储；下载使用 `no-store, no-cache`，但这无法删除接收方自行保存的文件。
- 每次成功准备下载必须先保存安全审计；下载不改变卡密状态，不证明接收方已经成功保存文件。
- 长期保留提高可找回性，也延长了数据库与主密钥同时失陷时可泄露的卡密历史。备份包含两者且未额外加密，必须另行进行受控加密、离线保管和访问审计。
- 原 AES-GCM purpose 与 `master_encryption_key` 必须保留。Cookie 的 ASP.NET Data Protection key ring 不是 CSV 解密密钥；直接替换主密钥会破坏旧归档和签名私钥解密，当前实现不提供自动多密钥轮换。
- 旧版已清空或丢失的密文不能从卡密 HMAC 反推。非空密文也不保证可解密，格式损坏、篡改或密钥错误仅返回通用不可用提示，不自动删除或重新生成卡密。

## 6. 签名密钥边界

领域模型使用 ES256。服务端私钥以受保护字节保存，公钥可分发给客户端。

- 私钥不得进入客户端、日志、OpenAPI 示例或普通备份报告；
- 应用解密密钥与数据库备份组合后可恢复私钥，因此两者应共同视为高敏感；
- 新公钥先传播，再启用新私钥签名；
- 退休不等同撤销；历史验证窗口内通常仍需保留退休公钥；
- 紧急撤销要定义离线客户端行为，不能假设所有客户端实时在线；
- ES256 签名不加密许可证内容。

## 7. 反向代理与转发头

Caddy 会设置标准代理头并添加 `X-Real-IP`。应用必须只信任来自部署内 Caddy 的转发头。若应用直接信任任何远端提供的 `X-Forwarded-For/Proto/Host`，攻击者可能伪造来源、scheme 或安全决策。

当前 HTTP 模式不得发送 HSTS。`enable-https` 的首次事务明确保持 `HSTS_ENABLED=false`，避免失败回滚到 HTTP 后浏览器仍被长期策略锁定。只有迁移真实 HTTPS、验证证书续期、可用性告警和回滚能力后，才可用 `licensectl enable-hsts --confirm-enable-hsts ENABLE-HSTS` 显式启用 30 天策略；默认不包含子域名。服务器可以停止继续发送 HSTS，但不能远程清除浏览器已经缓存的策略。

## 8. 主机加固建议

- 使用支持期内的 Ubuntu/Debian 和 Docker；
- 自动或受控及时安装安全更新，并安排重启；
- SSH 禁止口令登录，限制管理来源，保护 sudo；
- 使用云安全组和主机防火墙双层最小开放；
- 限制 Docker 组成员；Docker 组近似 root；
- 监控磁盘、内存、OOM、容器重启、健康状态和备份新鲜度；
- 主机时间使用受保护的 NTP/chrony；
- 避免在同一 2 GiB 主机运行不受信任或高争用工作负载；
- 不在生产主机直接进行任意源码构建；优先拉取经过 CI 签名、扫描和固定 digest 的镜像；
- 对 `/etc/license-platform`、systemd unit、Compose 文件和 Caddyfile 做文件完整性监控。

## 9. 事件响应

疑似泄露时：

1. 保存主机、容器、代理、应用和身份系统证据，避免先清理；
2. 从可信控制面限制公网入口；
3. 判断 HTTP 链路、管理员账号、数据库口令、应用解密密钥、签名私钥和备份是否受影响；
4. 不要只轮换一个口令就宣布结束；
5. 若签名私钥可能泄露，执行密钥撤销/轮换和客户端公钥更新计划；
6. 从已验证、攻击发生前的可信备份在隔离环境恢复；
7. 重建主机和 Docker 信任根，而不是继续信任已失陷系统；
8. 记录受影响许可证、客户和法务/通知义务；
9. 恢复后强制 HTTPS，复盘根因和检测缺口。

## 10. 安全验收最低线

生产验收前至少满足：

- [ ] 域名 HTTPS，真实证书验证成功，无 HTTP 降级；
- [ ] 应用和所有基础镜像固定 digest；
- [ ] 镜像漏洞扫描、SBOM 和来源证明已审阅；
- [ ] 后台 MFA/RBAC/会话策略已验证；
- [ ] 数据库和 8080 未发布；
- [ ] secrets 权限和备份加密已验证；
- [ ] 备份异地、不可变，并完成恢复演练；
- [ ] ES256 密钥轮换和撤销演练完成；
- [ ] API 输入、认证授权、限流、审计和日志脱敏通过安全测试；
- [ ] 升级、应用回滚和数据库恢复的兼容边界已演练。
